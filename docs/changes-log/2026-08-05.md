# Changelog - Working Structure, Toolchain Modernization & Documentation System (2026-08-05)

## Overview

1.0.0 shipped configuration but no structure: `src/` held a single `index.ts` with two demo functions, so the first
question anyone forking the template asks — where does code go — had no answer in the repository itself.

This session gives it one, and repairs the tooling meant to keep the answer honest. The prompt for the second half was
auditing downstream use of 1.0.0: its defects were being copied forward untouched, because not one of them fails a
build. A `lint:run` that checks nothing still exits 0. A `dev` script nobody runs is never noticed. A `main` pointing at
an unloadable bundle is invisible until someone calls `require()`.

That is the governing constraint for a template, and worth stating plainly: **a defect here is not one bug, it is one
bug per library.** Tooling in this repository is production code.

Considered and deliberately not adopted:

- **A JSDoc convention-checking script.** TypeDoc's own validation now fails the build on undocumented exports and
  broken links, which covers the defects that actually matter. A second script enforcing style on top of it is more
  maintenance than the remaining margin justifies.
- **`.npmignore`.** `package.json#files` already governs the tarball and takes precedence over it, so adding one gives
  two sources of truth and no extra control.

## Added

### A layered `src/`

- `src/core/` (domain), `src/types/`, `src/constants/`, `src/exceptions/`, `src/utils/`, each with an `index.ts` barrel
  carrying an `@module` block that states what belongs in the layer and what may import it. `core/` is a placeholder
  name, documented as the thing to rename when forking.

  `src/index.ts` is now a barrel with no implementation. Making it one means the published surface is something you can
  see rather than something you have to read the codebase to determine — which is also what lets TypeDoc document
  exactly the set a consumer can reach.

### `LibraryException`

- `src/exceptions/LibraryException.ts` — a base exception carrying a stable `code` to branch on and an optional `cause`
  to keep a wrapped failure attached. Without one, a library's only signal to a caller is message text, which is prose
  and gets reworded.

  `cause` is declared on the class rather than accepted through `ErrorOptions`, because the two-argument `Error`
  constructor is ES2022 and this project's `lib` is ES2020 — declaring the field keeps chaining available without moving
  the language baseline for every consumer. `Object.setPrototypeOf` is there because without it `instanceof` returns
  `false` for subclasses in the downlevelled CommonJS bundle, which would defeat the entire point of having a base
  class.

### A lint-enforced layer boundary

- `eslint.config.ts` restricts `types/`, `constants/`, `exceptions/`, and `utils/` from importing `@/core`. The arrow
  runs one way, which is what lets any of the four be read, tested, or lifted into another package without dragging the
  domain along.

  It is a lint rule rather than a note in a comment because the whole value of a boundary is that it holds under later
  edits — a convention survives only as long as everyone remembers it, and the import that breaks it is
  indistinguishable from every other import at the point it is written.

### Documentation site

- `docker/docs.Dockerfile`, `docker/docker-compose.docs.yaml`, `docker/nginx/{index.html,default.conf}` — nginx serving
  a landing page plus `/docs/` (TypeDoc), `/coverage/` (Jest HTML), and `/book/` (HonKit). Published on `80:80`, so the
  URL carries no port.

  The image runs the full `npm run test` rather than lint alone: the coverage report it serves is produced by that same
  step, so a build that skipped tests would ship an empty `/coverage/`.

  Compose gets an explicit project name. Without one it derives the name from the directory holding the compose file —
  `docker/` — which every project using this layout would share, so two of them collide on container names and share a
  network.

### Documentation gates

- `typedoc.json` gains `treatWarningsAsErrors` with `validation.notDocumented`, `invalidLink`, `notExported`, and
  `rewrittenLink`; `skipErrorChecking` becomes `false`. On its first run it failed the build on a `README.md` link to
  `docs/changes-log/2026-apr-19.md`, a file renamed earlier in this same session — precisely the class of rot it exists
  to catch. It later caught a second one: two community documents the docs image was not copying, which the README links
  to.

  `entryPoints` stays `./src/index.ts` rather than expanding over `./src`. For a library the API reference should mirror
  what consumers can import; internals are not documented for people who cannot reach them.

### Tests

- `test/core/Metadata.spec.ts` and `test/utils/Text.spec.ts`. `test/index.spec.ts` is **unchanged** and still passes,
  which is the evidence that the public surface survived the restructure. Coverage is 100% of statements, branches, and
  lines.

## Changed

### Module resolution

- `baseUrl: "src"` → `paths: { "@/*": ["./src/*"] }`, with `moduleDirectories` in Jest replaced by a matching
  `moduleNameMapper`.

  `baseUrl` made `import … from 'types'` resolve to `src/types`, but `types`, `constants`, and `utils` are all real
  published packages — the meaning of such an import depends on what happens to be installed. `paths` needs no `baseUrl`
  as of TypeScript 4.4, and the `@/` prefix cannot collide.

  Verified end to end: `tsc --noEmit` resolves, Jest resolves, and no bare `@/` specifier survives into any bundle.

### Toolchain

- ESLint 8.23.1 → 10 with `.eslintrc.json` + `.eslintignore` replaced by `eslint.config.ts`; `@typescript-eslint` 5 → 8;
  TypeScript 4.7.4 → 5.0.4; Jest 29 → 30; TypeDoc 0.23 → 0.28. Plus an `overrides` block pinning vulnerable transitives.

  Two rule renames were forced by `@typescript-eslint` v8: `@typescript-eslint/semi` was removed outright (already
  disabled, so simply gone) and `no-empty-interface` became `no-empty-object-type`, kept disabled as before.
  `@typescript-eslint/no-unused-vars` is kept an error with an `^_` escape — an unused import in a library is dead
  weight that ships.

  The install needed the lockfile regenerated. The old lock still resolved `eslint-config-typescript` →
  `@typescript-eslint@5`, which cannot coexist with ESLint 10.

### Documentation

- HonKit replaces GitBook. `gitbook-cli` is abandoned and no longer installs on any current Node; the image building it
  was pinned to `node:10-buster`. `docs/book.json` also had `root: "./docs"` while already sitting inside `docs/`.
- `docs/` restructured to `getting-started/` + `guides/` + `reference/`. A library's documentation needs an Installation
  and a Quick Start before anything else, and `reference/directory-structure.md` is the page a fork reaches for first.
- `docs/README.md` becomes an index with per-directory tables and an explicit statement of which docs are living and
  which are point-in-time records.
- `docs/changes-log/2026-apr-19.md` → `2026-04-19.md`, and `docs/release-notes/1.0.0.md`'s release date corrected from
  "May 8, 2026" to 2026-04-19, which is what `CHANGELOG.md` and the changes-log entry both say.
- `docs/guides/publishing.md` records the release-notes section skeleton as a table, after 1.1.0 was first written in a
  shape that did not match 1.0.0's. A format that exists only as an example drifts the first time someone writes from
  memory.

### Coverage

- `coverageReporters` becomes `lcovonly` + `html` so the site can serve a browsable report at `/coverage/` while Codecov
  still receives `lcov.info`; `collectCoverageFrom` is scoped to `src/**`.

### `tsconfig.test.json`

- Its `types` array sat outside `compilerOptions`, where TypeScript ignores it. Moved in, with `@types/jest` added
  alongside `@types/node` — without which moving it would have removed the Jest globals from the spec compilation.

## Fixed

### The packaging bug

- `package.json` declared `"type": "module"` while `main` pointed at `lib/index.min.js`. Under `type: module` Node reads
  every `.js` file in the package as ESM, so the CommonJS bundle parsed as ESM and `require()` of the package returned
  nothing usable.

  Nothing caught it. The build succeeded, the suite passed, and TypeScript was satisfied, because none of the three ever
  loads the packaged form. It surfaced from `node -e "require('./lib/index.min.js')"` while verifying the new `exports`
  map, and that check is now a step in the publishing guide.

  CommonJS now emits to `lib/index.min.cjs` and UMD to `lib/index.min.umd.cjs`. Both extensions are unambiguous whatever
  `type` says.

### Scripts

- `lint:run` was `eslint -c .eslintrc.json --ext=.ts,tsx` with no path argument, so ESLint checked nothing. Now
  `eslint src`.
- `npm test` was `npm run lint & npm run test:run`; `&` backgrounds the linter on POSIX shells, so a lint failure never
  reached the exit code. Now `&&`.
- `dev` invoked a runtime CLI that was not among the dependencies and has no meaning in a library. Now
  `rollup -c rollup.config.ts --watch`.

### Packaging

- Added an `exports` map so modern Node and bundlers resolve the package rather than falling back to `main`/`module`.
- Removed `peerDependencies: { rollup }`. A library built with Rollup does not require its consumers to install Rollup.
- UMD global renamed to `TemplatesProjectNodejs`. It had been carrying the name of an unrelated project since the
  initial commit.

## Removed

- The root `Dockerfile` and `docker-compose.yaml`. The image built `lib/` and `dist/`, then ran `tail -f /dev/null` — it
  served none of what it built, and a library has nothing to containerize.
- `docker/book.Dockerfile` and `docker/docker-compose.book.yaml`, the `node:10` GitBook build.
- devDependencies `@eslint/config-array`, `eslint-plugin-import`, and `eslint-config-typescript`. No configuration
  referenced any of them.
- The Deployment section of `AGENTS.md`, which described an Azure Static Web Apps workflow, a
  `staticwebapp.config.json`, and a `DEPLOYMENT.md`. None of the three exists in this repository, and git history shows
  none ever did.

## Notes

`npm audit` reports two high-severity advisories in `immutable <= 4.3.8`, reached only through `honkit`, with no
upstream fix available. Both are denial-of-service classes in a documentation-build devDependency that never enters the
published tarball.
